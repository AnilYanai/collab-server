1. EXECUTIVE SUMMARY & PROBLEM IDENTIFICATION
--------------------------------------------------------------------------------
In high-throughput collaborative servers handling real-time audio, video, or
canvas state, every microsecond of pipeline latency counts. 

Prior to this fix, the message dispatch and broadcast pipeline suffered from
Bottleneck 2 ("The Quadruple Room Search"). For EVERY single incoming packet
(client broadcast or peer broadcast), the server repeatedly performed redundant
lookup queries against the exact same ConcurrentHashMap (sessions) within
SessionRegistry using String sessionId:

  Lookup 1: sessionRegistry.saveSessionState(sessionId, rawBytes)
            --> searches sessions.get(sessionId)
  Lookup 2: sessionRegistry.getUDPConnections(sessionId)
            --> searches sessions.get(sessionId)
  Lookup 3: sessionRegistry.getTCPConnections(sessionId)
            --> searches sessions.get(sessionId)
  Lookup 4: sessionRegistry.getPeerServers(sessionId)
            --> searches sessions.get(sessionId)
  (Optional Lookup 5: sessionRegistry.getLocalClients(sessionId) if TCP/UDP empty)

THE COST AT SCALE:
- At 6,000 packets/second:
  4 lookups * 6,000 = 24,000 ConcurrentHashMap searches every single second
  (1,440,000 map queries every minute).
- Although ConcurrentHashMap.get() is non-blocking (lock-free), it is NOT free:
  * Key object hashing (spread Murmur/hash calculation of the String sessionId)
  * Array indexing & volatile memory read barriers on table buckets
  * Linked-node / tree-node traversal
  * Object reference and string .equals() comparisons
  * Cache-line thrashing across multi-core CPU L1/L2 caches
- Race condition risk:
  Querying the map 4 separate times breaks state atomicity across the 4 steps:
  if a session is closed or modified between Lookup 1 and Lookup 4, the steps
  operate on inconsistent room states.

3. ARCHITECTURAL SOLUTION (SINGLE SESSION FETCH PATTERN)
--------------------------------------------------------------------------------
Instead of passing String sessionId down the chain and searching the map at each
sub-step, we resolve the Session object EXACTLY ONCE at the entry point, and pass
the live Session instance directly to state preservation and broadcast fan-out.

1. Exposed Direct Session Accessor in SessionRegistry:
   Added public Session getSession(String sessionId), returning sessions.get(sessionId).

2. Added Overloaded Direct-Session Fan-Out Methods in BroadcastService:
   - broadcastFromClient(String senderConnectionId, Session session, byte[] rawBytes)
   - broadcastFromPeer(String peerConnectionId, Session session, byte[] rawBytes)
   - broadcastAll(Session session, byte[] rawBytes)
   Inside these methods, session.getUDPConnections(), session.getTCPConnections(),
   session.getLocalClients(), and session.getPeerServers() are retrieved directly
   from the already-resolved Session object with ZERO map searches!

3. Updated PacketDispatcher Inbound Handlers:
   Resolves Session session = sessionRegistry.getSession(sessionId) ONCE.
   Then calls session.saveState(rawBytes) and passes session to BroadcastService.
   Retains backward-compatible fallback for mock environments where getSession()
   is unstubbed.

5. HOW THIS BOOSTS PERFORMANCE
--------------------------------------------------------------------------------

1. 75% Elimination of Hash Map Operations:
   - Before: 4 (or 5) lookups per packet.
   - After: Exactly 1 lookup per packet.
   - At 6,000 packets/sec: Lookups drop from 24,000/sec to 6,000/sec.
     Eliminating 18,000 ConcurrentHashMap searches every single second.

2. L1 / L2 CPU Cache Locality & Zero Memory Bus Contention:
   - In ConcurrentHashMap.get(), the CPU must access table array buckets and
     read volatile pointers. Doing this 4 times for different methods flushes
     registers and causes unnecessary cache line reloads.
   - Holding the Session reference in a local register/stack variable keeps the
     session object in L1/L2 cache throughout the entire fan-out pipeline.

3. Lower CPU Branching & Zero String Hash Computation:
   - String hash code calculations and string equality loops (.equals()) are
     bypassed for lookups 2, 3, and 4.
   - Reduces instruction counts per packet in the hot network loop.

4. Session State Atomicity & Thread Safety:
   - By capturing the Session instance once at entry, all downstream actions
     (state preservation and connection iteration) are guaranteed to operate
     on the exact same room instance, avoiding transient race conditions if
     another thread removes or closes the room during packet transit.
